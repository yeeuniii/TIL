
마케팅 흐린 눈 하면서 살다가 모두가 떠나고 나서야 이제는 진짜 이해해야 됨을 자각하였다. 
마케팅 도메인 지식을 이해한 대로 하나씩 정리하는 문서이다. 

광고 네트워크와 미디에이션은 다르다. 
전자는, 광고주의 광고 수요를 모아 앱·웹의 광고 지면에 공급하는 곳이고
후자는, 여러 광고 네트워크를 연결하고, 광고 요청마다 어느 네트워크를 사용할지 결정하는 플랫폼이다. 
미디에이션의 정의가 중개라고 생각하면 이해하기 조금 쉬워진다. 

예를 들면, Applovin vs Applovin Max 이다. 
applovin, unity, vungle 등이 광고를 공급하면 admob, applovin max 가 그 중 어떤 광고를 보여줄 지 결정한다. 

또 계속 헷갈렸던 개념 중 하나는 **광고 선택 방식**인, Waterfall과 Bidding 이다. 
한 단어로 정리하면, Waterfall은 순서대로 호출, Bidding은 경매이다. 
기본 Waterfall 중심의 미디에이션에 Bidding이 추가되었다. 우리 회사는 두 방식 모두 사용한다. 
Waterfall은 '예상 가격으로 정한 순서'를 따라 광고를 요청하는 방식이다. 

```
A: 설정 eCPM $10 → 광고 없으면 B: $8 → 광고 없으면 C: $5
```

Bidding은 '이번 광고 기회에 제시한 가격'을 비교하는 방식이다. 

```
A: 이번 입찰 $6 / B: $9 / C: $7 → 적격 입찰 중 B 선택
```
Open Bidding은 Google의 Bidding 구현 중 하나이다.

이번 이슈의 시작은 admob 미디에이션을 applovin max로 이관하면서 max의 매출이 누락되었다는 것이었다. 
로직을 뜯어보니 max에서 applovin 데이터만 변환하고 있었고, 
raw 데이터에는 vungle, unity 등 여러 광고 네트워크의 매출이 있는 것을 확인하였다. 

첫번째 걸림돌은 max가 중개한 매출을 누가 지급하는지를 파악이었다. 
MAX에서는 AppLovin 자체 광고 매출은 AppLovin이, 다른 네트워크의 광고 매출은 해당 네트워크가 지급한다. 반면 AdMob은 다수의 Bidding 네트워크 매출을 대신 지급하지만, 네트워크가 직접 지급하는 Direct Pay 예외도 있다. 따라서 광고 공급 네트워크와 지급 주체는 따로 확인해야 한다.
히스토리를 알고 있는 사람들을 찾아가며 위 결론을 알아내려고 했다. 하지만 위 정보는 max 공식 문서에서도 찾을 수 있으며, 회사에 알고 있는 사람도 없어서 시간이 더 오래 걸렸다. 
AI가 서치도 잘 해주는 세상에서 너무 안일한 태도였던 것 같다.

두번째는
bidding을 admob이 정산해주는 네트워크의 매출 데이터를 어떤 방식으로 취합할 것인지였다. 
처음에는 Network API를 정산 대조의 기준으로 사용할 수 있을 것이라 생각했다. 하지만 이번에 수집한 raw에는 미디에이션 경유 여부나 지급 주체를 직접 구분하는 필드가 없었다. 일부 placement는 AdMob과 MAX가 공유하고 있어, ID만으로 AdMob 지급분을 정확히 제외하기 어려웠다.


Unity의 Network raw와 AdMob 전체(Bidding·Waterfall) + MAX 합계를 비교했을 때 금액 차이가 있었다. 별도로 Vungle 인보이스와 대조했을 때는 AdMob Waterfall + MAX 합계가 가까웠다. 다만 이것만으로 직접 raw의 지급 범위나 차이 원인까지 확정한 것은 아니다.

AdMob Bidding 매출은 기존 `*_admob` pid로 별도 유지하고, 일반 네트워크 pid에는 AdMob Waterfall + MAX 매출을 반영하기로 했다. 직접 Network raw는 검증용으로 보존하되 추가 합산하지 않는다
